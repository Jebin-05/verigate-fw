1. Engineering principles (non-negotiable)

Rule 1 — Fail closed
If a check cannot be completed (chain unreachable, missing field, parse error), the answer is reject or defer, never approve. This applies to every function in gateway/stage1 and gateway/policy. Tests must cover the "input missing" and "dependency down" branches.
Rule 2 — Measured, never fabricated
Every number in the paper, README, or a PR description comes from a file under evaluation/results/ produced by a runner with a recorded git SHA. Hand-typed numbers are a project-ending integrity failure. If you have not measured it, write "not yet measured".
Rule 3 — No secrets in git, ever
Private keys, RPC URLs with tokens, API keys: only in .env (ignored) or GitHub Actions secrets. gitleaks runs on every commit and every PR. The keys in .env.example are Hardhat's public well-known test keys and must stay the only keys in the repo.
Rule 4 — Deterministic decision path
Anything that contributes to the verdict R must be reproducible: same inputs → same bytes. ONNX models with pinned inputs, canonical JSON, fixed seeds. The LLM never touches R (ADR-0002).
Rule 5 — Small, reviewed, green
One logical change per PR, ≤ ~400 lines of diff where possible, CI green, one approval, squash-merge. No direct pushes to main (branch protection enforces it).
Rule 6 — Write it down
Every design decision that a reviewer could question gets an ADR (docs/adr/). Every module has a docstring saying what it is responsible for and what it is not. Every public function has a docstring or NatSpec.
Rule 7 — Portable by default
The whole system must start on any machine with Docker from a fresh clone using make up, and prove itself with make smoke. No absolute paths, no "install X first" beyond Docker, no machine-specific config outside .env. See section 16 and ADR-0004.
Why so strict?
Two audiences will judge this work: an evaluation panel and paper reviewers. Both look for reproducibility and honesty first. Discipline in the codebase is what makes "anyone can re-run this and get the same result" a true statement.

Python package structure rules

  • Single installable package verigate under src/ (src-layout: tests import the installed package, never the working directory).
  • Each area has __init__.py with a one-line docstring of responsibility; large areas have a README.md table of modules (see common/README.md).
  • Dependency direction: common ← ml ← gateway; publisher, fleet, attacks depend on common only (attacks may import fleet). Never import gateway from fleet or vice-versa — they talk over HTTP.
  • Entry points are declared in pyproject.toml (verigate-publish, verigate-gateway, verigate-fleet, verigate-attack, verigate-train). CLIs use Typer and live in <area>/cli.py.

Example — the shape every Stage-1 check takes

@dataclass(frozen=True)
class CheckResult:
    name: str
    ok: bool
    reason: str | None = None

def check_version_monotonic(manifest: Manifest, device: DeviceState) -> CheckResult:
    """Reject any release whose version is not strictly greater than the installed one.

    Prevents rollback attacks (Guide §5, check #4). Pure: no I/O.
    """
    if manifest.version <= device.installed_version:
        return CheckResult("version_monotonic", False,
                           f"{manifest.version} <= installed {device.installed_version}")
    return CheckResult("version_monotonic", True)

4.3 TypeScript / React (dashboard) and Hardhat scripts

  • TypeScript strict; eslint (typescript-eslint recommended, react-hooks); prettier (2 spaces, semicolons, single quotes).
  • Components are function components; state via zustand; server data via a typed api/ client generated from the gateway's OpenAPI (openapi-typescript).
  • The dashboard is read-only on-chain and has no private keys; all writes go through the gateway API (ADR-0003).

4.4 Cross-language invariants

Golden vectors
Canonical JSON, manifest hashing, Merkle leaves and Ed25519 signatures are computed in Python (gateway) and verified in Solidity/TypeScript (contracts, dashboard). tests/fixtures/canonical/*.json holds input → expected bytes/hash pairs. Both the pytest suite and the Hardhat suite load the same files. If you change a hashing rule, you change the fixtures, and both suites fail until both sides agree.

5. Git workflow

5.1 Branching — trunk-based

  • main is always releasable and protected: PR required, CI required, linear history, no force-push.
  • Short-lived branches from main: feat/<area>-<desc>, fix/…, docs/…, refactor/…, eval/…, ci/…. Example: feat/stage1-expiry-check. Lifetime target: ≤ 3 days.
  • Rebase on main before opening the PR (git fetch && git rebase origin/main). Squash-merge; delete branch.
  • Tags: vMAJOR.MINOR.PATCH (SemVer). Tagging triggers the release workflow.

5.2 Commits — Conventional Commits (enforced by commit-msg hook)

<type>(<scope>): <imperative summary ≤ 72 chars>

[body: what and why, not how; wrap at 100]
[footer: Closes #12 · Checklist: P3-04 · BREAKING CHANGE: …]

types : feat fix docs test refactor perf chore ci build eval
scopes: contracts publisher gateway stage1 stage2 policy verdicts fleet ml attacks dashboard infra eval docs

Examples: feat(stage1): add manifest expiry check (P3-01) · fix(contracts): reject weights not summing to 1e4 · eval(gas): batching vs per-device, 5 reps on sepolia.

5.3 Pull requests

  • Use the template (.github/PULL_REQUEST_TEMPLATE.md). Fill "How it was tested" with the actual commands and observed output.
  • Reference the checklist ID and tick it in CHECKLIST.md in the same PR.
  • Reviewer checklist: does it fail closed? are error branches tested? any env access outside settings? any number not traceable to results/? docstrings present? ADR needed?
  • CI must be green. Do not merge with "will fix in follow-up" on a red check.

5.4 Solo-developer note

If you are the only developer, still open PRs and self-review the diff on GitHub the next morning. The PR record is your audit trail for the panel ("show me how the rollback check was tested" → link to PR #17).

10. Phase-by-phase build guide

Each phase lists: goal · key design constraints · Definition of Done. Item IDs map to CHECKLIST.md.

P0 — Repository & tooling (week 1)

Goal: fresh clone → make bootstrap && make test-all green → first push → CI green → branch protection on.

  • Bootstrap the dashboard with Vite (npm create vite@latest . -- --template react-ts inside dashboard/), add eslint + prettier, ensure npm run lint and npm run build exist.
  • Commit lockfiles — CI uses npm ci, which requires them.
  • Add a LICENSE (MIT recommended for a research artefact you want cited).

DoD: P0-06 … P0-12 ticked; four workflows visible and green on main.

P1 — Common library & contracts (weeks 1–2)

Goal: the cryptographic and on-chain foundation, fully tested, before any service logic.

  • Canonical JSON first. Everything signed/hashed depends on it. Write the golden vectors, then the Python, then the TypeScript helper used by Hardhat tests.
  • Manifest model: extra="forbid", frozen=True, SemVer-typed version, ISO-8601 UTC expiry, CIDs validated as CIDv1.
  • Contracts in dependency order (see contracts/contracts/README.md). Define interfaces (I*.sol) first so the gateway bindings can be generated early.
  • FirmwareRegistry.register must: check caller has PUBLISHER_ROLE and is ACTIVE; enforce version strictly greater than the publisher's last version for that deviceModel; store keccak256(canonicalManifest); emit NewRelease(releaseId, publisherDid, version, manifestHash).
  • VerdictRegistry.commitBatch(root, count, modelHash) stores root + block + gateway; verifyLeaf(root, leaf, proof) view; staleByModel(modelHash) view returns batch ids whose model is revoked (join with ModelRegistry).
  • PolicyContract: weights as basis points summing to 10 000; thresholds as basis points; version increments per change; event carries old/new.
  • Deploy script is idempotent and writes addresses both to JSON and .env (localhost only).

DoD: contract coverage ≥ 95 %, slither clean, gas report in PR, Python integration test deploys and round-trips a record, threat model table filled.

P2 — Publisher CLI (week 2)

  • Typer CLI; every command prints a JSON result (machine-readable for tests and the demo script).
  • release = hash files → put on IPFS → build manifest → sign → put manifest → register on-chain → print releaseId, CIDs, tx hash. Each step idempotent (re-running with the same inputs is safe).
  • Fixtures: three versions of a toy firmware (a few hundred KB of deterministic bytes + a real ELF header) with SBOMs, so Stage 1/2 tests have realistic inputs.

DoD: integration test runs the full publish flow; verigate-publish --help is documented in README.

P3 — Gateway Stage 1 & fleet (weeks 3–4)

  • Stage 1 checks are pure functions over (Manifest, OnChainRecord, DeviceState, RevocationView, now). The runner fetches inputs via injected clients, then calls the checks. First failure stops (fail-closed) but the result lists the failing check name — the dashboard shows it.
  • Event listener: poll NewRelease from last_processed_block (persisted), exponential backoff on RPC errors, never skip blocks.
  • Device emulator: DeviceState persisted as JSON under fleet/state/<deviceId>/nvs.json plus slot_a.bin/slot_b.bin. Device re-verifies hash and signature itself before switching slots. Install receipt = Ed25519 signature over canonical {deviceId, releaseId, version, installedAt}.
  • Device ↔ gateway protocol: HTTP JSON, every message signed, nonce + timestamp window against replay.
  • Attack scripts for the six Stage-1 attacks; each has an e2e test.

DoD: demo shows tamper / forge / stolen-key / rollback / freeze / sbom-swap all rejected with the right reason.

P4 — Verdicts, batching, reputation, dashboard (weeks 5–6)

  • Verdict record schema (pydantic, frozen): releaseId, deviceId, modelHashes, featureHash, r_sbom, r_img, reputation, R, verdict, rationaleCid, gatewaySig, ts. Leaf = SHA-256(domain ‖ canonical(record)).
  • Batching: accumulate up to N verdicts or T seconds, build tree, commitBatch; store proofs locally; expose /verdicts/{id}/proof.
  • Policy engine reads PolicyContract (cached per block); returns DEFER on any dependency error.
  • Dashboard: pages listed in dashboard/README.md; live log over websocket; attack buttons.
  • Tag v0.1.0 — the crypto-path baseline that is demonstrable on its own.

P5 — SBOM risk model (weeks 7–8)

  • Data: pin upstream releases in data/sources.yaml; fetch script; syft → CycloneDX; record every file hash in data/MANIFEST.sha256.
  • Vulnerability clients with disk cache and a recorded snapshot date; offline mode for demos.
  • Features (pure, golden-vector tested): max CVSS, sum EPSS, KEV count, n components, n outdated, mean dep age (days).
  • Model: HistGradientBoostingRegressor; target defined in the model card (state exactly what the label is and how it was derived). Seed 42. Export ONNX; test ONNX vs sklearn equality.
  • Baseline scorer (deterministic CVSS/EPSS/KEV formula) for the evaluation comparison.

DoD: model card complete, hash in MANIFEST, registered on-chain, verdicts carry it, evaluation config produces AUROC/Spearman vs baseline.

P6 — Image anomaly, LLM explainer, model revocation (weeks 9–10)

  • Mutation generator with a documented catalogue (name, description, parameters, seed) — this is part of the paper's reproducibility.
  • Image features (pure): chunk entropy mean/std/max, printable ratio, section sizes and deltas vs previous version, header sanity flags, appended-bytes length.
  • Isolation Forest on benign releases only; evaluate per mutation class.
  • Explainer: Ollama client with strict JSON schema, one retry, timeout 120 s, LLM_ENABLED switch; output to IPFS; CID in the verdict. Never in R.
  • Model revocation: admin CLI → ModelRegistry.revoke → gateway job queries staleByModel → re-runs Stage 2 with successor model → new batch → dashboard shows before/after verdict delta.
  • Tag v0.2.0.

P7 — Evaluation (weeks 11–12)

11. ML & data discipline

  • Datasets are never committed. They are reproducible from data/sources.yaml + fetch script + mutation generator with fixed seeds, and their hashes are in data/MANIFEST.sha256 (committed).
  • Seeds everywhere: numpy, sklearn, mutation generator, train/test split. make train twice must produce byte-identical ONNX files (test this — it is what makes model hashes meaningful).
  • Model card per model (models/<name>.card.md): purpose · features (with units) · training data manifest hash · seed · hyper-parameters · metrics on held-out set · known failure modes · date · git SHA.
  • ONNX only at runtime. No pickles loaded by the gateway. modelHash = SHA-256(onnx bytes) is what goes on-chain.
  • Shipping a model version: train → card → make models-hash → PR (CI verifies manifest) → merge → admin registers hash on-chain → old hash remains, may be revoked later. Never overwrite a model file that has been registered; bump the file name (image_anomaly_v2.onnx).
  • Feature extraction is pure and golden-vector tested; any change is a new model version because the feature hash changes meaning.
  • Honest labels. The tampered set is synthetic; say so in the card and paper. Do not describe it as real-world malware.

12. Evaluation discipline

  • One YAML per experiment in evaluation/configs/: seed, fleet size, network, repetitions, model hashes, git SHA is auto-recorded.
  • Runner writes evaluation/results/<exp>/<timestamp>_<sha>/raw.csv, summary.json (median, IQR, n), env.json (CPU, RAM, Python/Node versions, contract addresses, tx hashes, vulndb snapshot date).
  • Results directories are append-only. Re-running creates a new directory; nothing is edited by hand. Results that were wrong stay, with a note in the next summary.
  • evaluation/figures.py is the only producer of figures; it reads results and writes evaluation/figures/*.pdf|png. Figures are regenerated in the P8 PR so they match the final results.
  • Timing: ≥ 5 repetitions, warm-up run discarded, report median + IQR, state the machine.
  • Gas: from hardhat-gas-reporter (local) and real receipts (Sepolia); report both and say which is which.
  • Attack matrix: one row per attack, columns = expected verdict, observed verdict, run count, pass rate. Any row that is not 100 % goes into the limitations section, not the bin.

13. Documentation & ADRs

  • README.md: what it is, quick start, layout, status link. Keep it under two screens; details go to docs/.
  • CHANGELOG.md: Keep-a-Changelog format; every PR adds a line under Unreleased; release moves it under the version.
  • ADRs (docs/adr/): number, title, status, context, decision, alternatives, consequences. Written when the decision is made, never edited after acceptance — superseded by a new one. Three exist already (manifest signing, LLM explain-only, dashboard stack). Expected next: batching parameters, reputation formula, version-comparison rules, mutation catalogue.
  • Threat model (docs/threat-model.md): table with asset · attacker · attack · mitigation · test that proves it. Every row links to a test file.
  • API docs are generated by FastAPI at /docs; contract docs by NatSpec (npx hardhat docgen optional).

16.2 Moving to a new machine — the ritual

1. Install Docker (Desktop on macOS/Windows-WSL2; docker-ce + compose plugin on Linux). Nothing else.
2. git clone <repo> && cd verigate-fw
3. make doctor            # fix every ✘ (usually: a port in use → set GATEWAY_PORT=8001 in .env)
4. make up                # first run builds images (~3–5 min); later runs are seconds
5. make smoke             # must print "✔ smoke test passed"
6. make llm-pull          # only if the machine has ≥ 12 GB RAM and you want the explainer live
7. open http://localhost:5173 (dashboard) and http://localhost:8000/docs (gateway API)
8. ./scripts/demo.sh      # (P4-08) the rehearsed attack sequence
Before a demo on someone else's PC
Do steps 1–5 the day before, on that PC. Pre-pull images (docker compose … pull) so no download happens live. Keep the recorded video fallback (P8-03) on a USB stick.

16.3 Rules that keep it portable (enforced in review)

  • Never hard-code a path, hostname or port. Read it from settings; default to a container-friendly value (0.0.0.0, service names like hardhat, ipfs).
  • Every new service gets: a pinned base image, a health check, depends_on … condition, a named volume if it has state, and an entry in .env.example for its port.
  • Anything that downloads at runtime (vulnerability data, LLM weights, firmware datasets) must have a cached/offline mode and a documented pre-fetch command.
  • Scripts are #!/usr/bin/env bash with set -euo pipefail, use only POSIX tools + docker + python3, and are run by CI so they cannot rot.
  • If a change breaks make smoke, the PR is red; fixing the smoke test is part of the change, not a follow-up.

#!/usr/bin/env bash
# Fresh-machine smoke test. Proves the whole stack starts from a clean clone with ONE command and reaches a verdict.
# Used by CI (portability job), by `make smoke`, and by you on any new laptop before a demo.
set -euo pipefail
cd "$(dirname "$0")/.."
COMPOSE="docker compose -f infra/docker-compose.yml --profile app"
cleanup() { $COMPOSE down -v --remove-orphans >/dev/null 2>&1 || true; }
trap cleanup EXIT

[ -f .env ] || cp .env.example .env
echo "▶ starting full stack"
$COMPOSE up -d --build
echo "▶ waiting for gateway health"
for i in $(seq 1 60); do
  if curl -sf "http://localhost:${GATEWAY_PORT:-8000}/health" >/dev/null; then break; fi
  sleep 2; [ "$i" -eq 60 ] && { echo "gateway never became healthy"; $COMPOSE logs --tail=50; exit 1; }
done
echo "▶ publishing fixture release v1.0.0 and verifying"
$COMPOSE run --rm -T gateway verigate-publish release \
  --fw /app/fixtures/releases/v1.0.0/firmware.bin --sbom /app/fixtures/releases/v1.0.0/sbom.json \
  --version 1.0.0 --model demo-device --expiry 2030-01-01T00:00:00Z --json > /tmp/release.json

VERDICT=$(curl -sf -X POST "http://localhost:${GATEWAY_PORT:-8000}/verify/${RELEASE_ID}" | python3 -c 'import json,sys; print(json.load(sys.stdin)["verdict"])')
echo "verdict: $VERDICT"
[ "$VERDICT" = "APPROVE" ] || { echo "expected APPROVE for a clean fixture"; exit 1; }
echo "✔ smoke test passed"

#!/usr/bin/env bash
# `make doctor` — one-screen diagnosis on ANY machine: versions, ports, docker, disk, RAM, .env, lockfiles.
set -uo pipefail
cd "$(dirname "$0")/.."
ok()  { printf "  \033[32m✔\033[0m %s\n" "$1"; }
bad() { printf "  \033[31m✘\033[0m %s\n" "$1"; FAIL=1; }
FAIL=0
echo "Toolchain"
command -v docker >/dev/null && docker compose version >/dev/null 2>&1 && ok "docker + compose plugin" || bad "docker compose missing (Docker Desktop on macOS/Windows-WSL2, docker-ce on Linux)"
command -v python3.11 >/dev/null && ok "python3.11" || bad "python3.11 missing (only needed for host-mode dev; docker mode does not need it)"
command -v node >/dev/null && [ "$(node -p 'process.versions.node.split(".")[0]')" -ge 20 ] && ok "node ≥ 20" || bad "node ≥ 20 missing (host-mode dev only)"
echo "Repository"
[ -f .env ] && ok ".env present" || bad ".env missing → cp .env.example .env"
[ -f contracts/package-lock.json ] && ok "contracts lockfile" || bad "contracts/package-lock.json missing (P0-07)"
[ -f dashboard/package-lock.json ] && ok "dashboard lockfile" || bad "dashboard/package-lock.json missing (P0-07)"
grep -rIl --exclude-dir=.git --exclude-dir=node_modules --exclude-dir=.venv "/home/[a-z]*/" . 2>/dev/null | grep -v '^./docs/' | head -3 | while read -r f; do bad "absolute home path in $f"; done
echo "Machine"
MEM=$(awk '/MemTotal/ {printf "%d", $2/1024/1024}' /proc/meminfo 2>/dev/null || sysctl -n hw.memsize 2>/dev/null | awk '{printf "%d",$1/1024/1024/1024}')
[ "${MEM:-0}" -ge 8 ] && ok "RAM ${MEM} GB (≥ 8 needed; 12+ with LLM)" || bad "RAM ${MEM} GB — run without --profile llm"
DISK=$(df -Pk . | awk 'NR==2 {printf "%d", $4/1024/1024}')
[ "$DISK" -ge 10 ] && ok "disk ${DISK} GB free" || bad "disk ${DISK} GB free (< 10 GB)"
echo "Ports"
for p in ${HARDHAT_PORT:-8545} ${IPFS_API_PORT:-5001} ${GATEWAY_PORT:-8000} ${DASHBOARD_PORT:-5173}; do
  (command -v ss >/dev/null && ss -ltn | grep -q ":$p ") && bad "port $p in use → override in .env (e.g. GATEWAY_PORT=8001)" || ok "port $p free"
done
[ "$FAIL" -eq 0 ] && echo "all good — run: make up" || { echo "fix the ✘ items above"; exit 1; }

# 0004 — Portable by default: one command runs the whole stack on any machine

**Status:** Accepted   **Date:** 2026-09-18

## Context
The project must be demonstrated on hardware we do not control (panel room PC, a reviewer's laptop, a fresh VM) and
reproduced by others for the paper. "Works on the author's laptop" is the most common FYP demo failure.

## Decision
- Every runtime component has a pinned Docker image (`infra/Dockerfile.app`, `.hardhat`, `.dashboard`; pinned base tags).
- `infra/docker-compose.yml` runs the full stack with `--profile app`; the LLM is an optional `--profile llm`.
- `make up`, `make smoke`, `make doctor` are the only commands a new machine needs; host Python/Node are for development only.
- No absolute paths in code or config; everything resolves relative to the repository root or a container path.
  Ports are overridable via `.env`. Line endings normalised via `.gitattributes`.
- CI has a `portability` job that builds all images and runs `scripts/smoke.sh` from a clean checkout on every PR.
- Datasets are regenerable (`data/sources.yaml` + scripts); models are committed; results carry `env.json`.

## Alternatives considered
- Host-only setup with a long README — rejected; drifts immediately.
- Kubernetes / Helm — rejected; overkill for a single-machine demo.

## Consequences
Image builds add ~3 min to CI. Windows users need WSL2 + Docker Desktop (documented). The smoke test doubles as the
first e2e test and as the pre-demo ritual on any new machine.

End of manual. Next deliverable: docs/srs/ — Software Requirements Specification.
